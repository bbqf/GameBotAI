# Research: Execution Log Retention Default & Long-Run Rotation

## R1: What does "hold retention" map to in the existing system?

- **Decision**: `ExecutionLogRetentionPolicy.RetentionDays` (`src/GameBot.Domain/Logging/ExecutionLogRetentionPolicy.cs`), currently defaulted to `60`. Change the default to `7`.
- **Rationale**: This is the only retention concept in the codebase (confirmed by searching for "retention" across the repo). `ExecutionLogRetentionPolicyRepository.SaveAsync` already clamps any explicitly-saved value to `Math.Max(1, ...)`, so no validation changes are needed — only the compiled-in default on `ExecutionLogRetentionPolicy.RetentionDays` and its `Default` static property.
- **Alternatives considered**: A brand-new "hold" concept distinct from retention — rejected; the user's own phrasing ("hold retention") plus the absence of any other retention-like setting in the codebase makes this the only reasonable mapping.
- **Compatibility**: `ExecutionLogRetentionPolicyRepository.GetAsync` returns `ExecutionLogRetentionPolicy.Default` only when no policy file exists yet or it fails to parse — so this change is purely a fresh-install/never-configured default and cannot silently change any existing deployment's already-saved value (FR-002).

## R2: How are execution log entries currently produced for a queue run, and where does "between sequences" live?

- **Decision**: A queue run is `QueueExecutionService.RunAsync` (`src/GameBot.Service/Services/QueueExecution/QueueExecutionService.cs:219`). It calls `_log.LogQueueStartAsync` once at the top, producing one root `ExecutionLogEntry` (`ExecutionType="queue"`) whose id becomes `rootId`. Every scheduled firing (at-start, once-per-run, every-step, timer, self-reschedule, relative, live, retry) funnels through the single private helper `RunOneSequenceAsync(sequenceId, rootId, index, ...)` (`QueueExecutionService.cs:611`), which builds an `ExecutionLogContext { RootExecutionId = rootId, ParentExecutionId = rootId, SequenceIndex = index, ... }` and calls `_sequenceExecution.ExecuteAsync(...)`, which itself calls `LogSequenceStartAsync`/`LogSequenceFinalizeAsync` to create the sequence's own `ExecutionLogEntry`, nested under `rootId` via `ExecutionHierarchyContext`.
- **Key implication for rotation**: There is **no single entry that grows over the life of a 24h+ run** — each sequence firing already gets its own file/entry, and they are linked only by sharing the same `RootExecutionId`. "Rotating the log" therefore means minting a **new `RootExecutionId`** (a new queue-level root entry) partway through a run, and pointing subsequent `RunOneSequenceAsync` calls at the new root instead of the old one — not literally splitting a file.
- **Where the cut is structurally clean**: All ~10 call sites of `RunOneSequenceAsync` sit inside `RunAsync`'s single sequential loop; `rootId` is currently a plain `var` closed over by every call site. The natural rotation point is a check made once, immediately before each `RunOneSequenceAsync(...)` call (or centralized as one helper both the loop and each call site route through), that closes out the old root entry and opens a new one if 24h have elapsed since the current segment's root was opened. This satisfies FR-005/FR-006/FR-007 (cut only between firings) with no new locking, because of R3.
- **Alternatives considered**: Splitting the *sequence* entry itself mid-run — rejected, contradicts "the cut should happen only in between the sequences" and there is no natural mid-sequence split point today. Introducing a new "run segment" entity/file distinct from the existing `queue`-type root entry — rejected as unnecessary; the existing queue-root entry already represents exactly "one contiguous stretch of a queue run" and reusing it (with two new linking fields) is the minimal change.

## R3: Concurrency — can two sequence firings within one queue run overlap, requiring locking around the rotation decision?

- **Decision**: No. Verified against `QueueExecutionService.RunAsync`: it is a single `Task.Run` per queue (`QueueExecutionService.cs:199`) running one sequential `await`-chained loop; every `RunOneSequenceAsync` call for that queue is awaited before the loop proceeds to consider the next firing. Feature 079 ("Concurrent Queue Execution") only made **separate queues** (each with their own `RunAsync` task, own `rootId`, own device session) safe to run side by side — it did not introduce concurrency *within* one queue's own firing sequence.
- **Rationale**: Because firings within one queue run are already strictly sequential, the rotation check-and-cut can be a plain inline step with no new synchronization primitive (no `SemaphoreSlim`, no lock) — it naturally runs in the gap between the `await` that finishes one firing and the call that starts the next. Two different queues rotating "at the same time" is not a race, because they never share a `rootId`/segment.
- **Alternatives considered**: Adding a per-queue-run async lock defensively "just in case" — rejected as unnecessary complexity for a boundary that is already exclusive by construction; would violate the constitution's code-quality guidance against unjustified complexity.

## R4: How should the rotation link be represented so it is a "structured, stable identifier field" (per clarification) rather than only text?

- **Decision**: Add two new optional fields to `ExecutionLogEntry` (and its DTO): `RotatedToExecutionId` (set on the closed-out segment's root entry, pointing at the new segment's root id) and `RotatedFromExecutionId` (set on the new segment's root entry, pointing back at the old segment's root id). Both are plain `string?` (the same shape as existing id fields like `ParentExecutionId`), so no new type is introduced.
- **Rationale**: Mirrors the existing pattern of plain string-id cross-references already used throughout `ExecutionHierarchyContext` (`RootExecutionId`, `ParentExecutionId`). Keeps the change additive and backward compatible — old entries simply have both fields `null` (FR-014), and existing `ExecutionLogEntry`/DTO consumers that don't know about the new fields are unaffected.
- **Surfacing to operators (SC-003)**: The existing `ExecutionLogDetailDto.RelatedObjects` (`RelatedObjectLinkDto`) mechanism (`src/GameBot.Service/Models/ExecutionLogs.cs`) already exists precisely to attach "jump to a related execution" links to a log entry's detail view. Populate one `RelatedObjectLinkDto` (`Label: "Continues in..."`/`"Continues from..."`, `TargetType: "execution-log"`, `TargetId: <id>`) from the new fields when building an entry's detail response, reusing the existing mechanism instead of inventing a new one. The web UI needs a small, additive rendering hook to show this link where it currently renders other related-object links (or, if that plumbing is not yet wired to the page, the minimal addition to wire it) — scoped as "surfacing the rotation markers/links," not a redesign, per the spec's Out of Scope note.
- **Alternatives considered**: Only writing a human-readable sentence into `Summary`/`Details` — rejected per the clarification decision (structured id needed for reliable navigation/testing, not just prose).

## R5: Where does the 24-hour clock start, and how is it tracked between firings?

- **Decision**: Track it as `TimestampUtc` of the currently-open segment's root `ExecutionLogEntry` (already recorded at creation). At the rotation check point, compare `DateTimeOffset.UtcNow - currentRootEntry.TimestampUtc > TimeSpan.FromHours(24)`. No new persisted state is required beyond the existing entry's own timestamp; the currently-active root id is already tracked in-memory on the run's `QueueRunHandle.RootExecutionId` (`QueueExecutionService.cs:221`), which becomes mutable (updated on rotation) instead of write-once.
- **Rationale**: Reuses data that already exists on every root entry; avoids a parallel "segment started at" field. Matches R2's finding that the queue-root entry already represents "one contiguous stretch."
- **Alternatives considered**: A separate stopwatch/timer counting elapsed run time — rejected as redundant with the entry's own creation timestamp, and timers don't survive a service restart the way a persisted timestamp does (if the service restarts mid-run, the next rotation check simply re-reads the still-persisted root entry's timestamp and behaves correctly, with no special-casing needed).

## R6: Retention interaction with a rotated (closed-out) segment (FR-013)

- **Decision**: No change needed to `ExecutionLogRetentionCleanupService`/`FileExecutionLogRepository` deletion logic. Each `ExecutionLogEntry` (including every segment's root entry) already carries its own independent `RetentionExpiresUtc`, computed from its own `TimestampUtc` at creation. A closed-out segment's root entry ages out and gets deleted on the existing per-entry schedule exactly like any other entry, regardless of whether a later segment (or the sequence entries nested under either root) still exists.
- **Rationale**: Retention already operates per-file/per-entry with no cross-entry dependency (confirmed in `FileExecutionLogRepository.cs`), so "independent expiry of segments" (FR-013) falls out for free from the existing mechanism — the only risk is a dangling `RotatedToExecutionId`/`RotatedFromExecutionId` pointing at a since-deleted entry, which the UI link-resolution must treat as "unavailable" (the existing `RelatedObjectLinkDto.IsAvailable`/`UnavailableReason` fields already exist for exactly this case).
- **Alternatives considered**: Making rotated segments immune to retention, or linking their expiry together — rejected; the spec explicitly requires independent expiry (FR-013), and the existing per-entry model already provides it with no extra work.
